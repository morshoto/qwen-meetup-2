## H1: Thinking response diagnosis

### Historical B/C reconstruction

The matched comparison is `artifacts/p3b3-compare-9a26aaf6340c`. Its comparison
manifest records B on five unused Exploration tasks and C on the same five
tasks with adapter
`cb2b646ae6aa80b51792e8f1bec3e0fe4a25d3f02c34c695961f752475dba229`.
The B and C request logs contain response hashes and token usage, but not HTTP
status/headers/body, generated bytes, `finish_reason`, or the server stop token.
Prediction artifacts retained the analysis text and extracted code for requests
that parsed; they did not retain the original reasoning blocks or the exact
HTTP content. `server-b.sqlite` and `server-c.sqlite` hold request hashes and
token reservations only. The missing values cannot be reconstructed from a
SHA-256 digest, so the report records them as unavailable instead of inferring
`stop` or `length`.

The offline report at
`artifacts/p3b-hardening-history-compare-9a26aaf6340c/report.json` was built
from both run directories, `llm_requests.jsonl`, `results.json`, and each
candidate prediction. No challenge or solution file was copied into the report.
Both runs returned 2xx JSON responses for every recorded request (the client
parsed each response and recorded usage); no HTTP status was retained. B made
29 calls with 73,265 prompt, 3,320 completion, and 76,585 total reported
tokens. C made 25 calls with 49,604 prompt, 693 completion, and 50,297 total
reported tokens. The separate client reservations were 201,383 tokens for B
and 148,603 for C.

### New response capture and offline diagnosis

New runs append the request metadata to `llm_requests.jsonl` and an owner-only
`llm_responses.jsonl` sidecar containing the HTTP status/headers, exact body as
base64 plus readable text, extracted generation, finish reason, usage, stop
reason, and intermediate parse report. Request logs contain only a prompt hash,
never prompt text. The response sidecar contains generated output only and is
created with mode `0600`; it does not copy task solutions or verifier labels.
The request ID joins the request and response records.

Synthetic, answer-free cases are stored in
`tests/fixtures/p3b_response_diagnostics.jsonl`. They exercise complete and
unclosed think tags, empty final output, model end token, partial generation,
plain and fenced code, JSON extraction and invalid JSON, transport failure,
HTTP budget rejection, sandbox failure, and verifier failure. The parser tests
in `tests/arc/test_response_diagnostics.py` make no model or HTTP calls.

Run the offline tool with:

```bash
uv run python -m src.cli.p3b_hardening \
  --diagnose-from-artifacts artifacts/<run-or-comparison> \
  --output artifacts/<separate-report>.json
```

It reparses raw sidecars when available. For historical artifacts it marks raw
response/finish/stop details unavailable and reconstructs only the parsed
analysis/code plus fields retained in the request ledger.

## H2: SFT data and inference alignment

`src/arc/prompting.py` owns the shared final-answer system message. Inference
and new SFT records use that same message; SFT targets contain only the final
assistant code. The installed MLX-LM 0.30.7 training entrypoint now uses chat
JSONL plus `--mask-prompt`, with a template wrapper that explicitly sends
`enable_thinking=False` in `off` mode. The preflight renders the actual chat
template in the configured Apple Silicon runtime and records every token's
prompt/completion loss region, template/config hashes, and prefix alignment.
Training stops and preserves the old adapter when that audit fails.

The historical Qwen3-8B artifact was audited with the installed 0.30.7 runtime.
Its 326-token example used mask offset 305 while the inference-aligned
thinking-off prefix is 309 tokens, so four empty think-marker tokens were
incorrectly included in its loss target. Its old two-message dataset also
lacked the canonical system message. That artifact is retained unchanged and
the audit is saved separately at
`artifacts/p3b-hardening-history-sft-audit.json`.

The real one-record low-data run also exercised the new path. Its generated
three-message SFT JSONL passed the installed runtime audit: 348 tokens total,
prompt mask and inference prefix both end at token 331, and all 17 loss tokens
are assistant completion tokens. The user message contains test inputs but
no test outputs. No validation loss was measured because no validation set was
provided. The audit is recorded with each candidate under
`artifacts/p3b-hardening-ablation-20261101/train-lr1e-05-steps*/training-run/sft_audit.json`.
New records are required to include the shared system prompt, user task JSON
without test outputs, and one assistant `transform` completion.

The policy follows Qwen's [thinking-mode template option](https://qwen.readthedocs.io/en/stable/getting_started/quickstart.html)
and MLX-LM's documented [`--mask-prompt` behavior](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md).

## H3: QLoRA ablation

`src/cli/p3b_hardening.py --ablate` runs base B, the retained historical C
adapter, and the fixed 1/3/5-step candidates at learning rate `1e-5` on the
same single verifier-approved record from the completed offset-260 B run. It
captures raw local synthetic code/JSON canary outputs, parser diagnostics,
finish reason, token counts, latency, adapter hash, training loss/runtime,
peak memory, and an `ablation_results.csv`. A 1,800-second aggregate cap
includes canary and training time. Each candidate has its own sealed training
artifact; the report hard-codes promotion off. This remains a low-data format
and wiring diagnostic, not generalization evidence.

The real run at `artifacts/p3b-hardening-ablation-20261101` used one verified
Exploration record (`a416b8f3`) with dataset SHA-256
`ef8fa72ff6c3a354f3cd6864fd357757d84ccbb58e20ca6dfb66a993bd431bed`. It
completed in 104.97 seconds. Base B passed 2/2 canaries; historical C passed
the code canary but failed the JSON canary (`invalid_json`); all trained
candidates passed 2/2 and had zero thinking-format errors.

## H4: P3-C verified solution collection

`configs/p3b.diagnostic-tasks.v1.json` records the five previously used
diagnostic IDs and their source comparison/protocol. The fixed P3-C B-only
batch is Exploration offsets 285–304; offsets 280–284 are excluded because
they are the diagnostic tasks: `57edb29d`, `b0722778`, `5582e5ca`,
`7953d61e`, and `44d8ac46`. `src/pipelines/p3a.py` checks the fixed batch
against the split and diagnostic manifest before creating a run, and the
collector re-verifies each proposed solution in the Docker runner. The model
receives test inputs without test outputs. Its manifest records the full
evaluated batch, candidate successes, unique verified tasks, and attempt
limit. Promotion holdouts now exclude diagnostic IDs and every task in the
training collection batch.

The collection profile budgets 5,400 wall seconds, 120 LLM calls, 2,000,000
tokens, 20 candidates, 500 sandbox starts, and two code attempts per task. A
separate training profile requires at least five distinct verified task IDs;
below that floor it skips training and preserves the previous adapter. The
collection and training commands are separate so collected solutions cannot
be fed back into inference-time prompts:

```bash
uv run --locked python -m src.cli.p3c collect \
  --config configs/p3c.collect.qwen8b.offset285.yml
uv run --locked python -m src.cli.p3c train \
  --config configs/p3c.train.qwen8b.yml \
  --collection artifacts/<verified-collection-directory>
```

The fixed offset-285 batch completed at
`artifacts/p3c-collect-qwen8b-offset285-9215cfeb3ad7` and its verified
collection is `artifacts/p3c-collection-offset285-20261101`. It scored all 20
tasks with zero runtime/scoring errors and pass@1 `0.0`; verifier-backed
re-execution admitted 0 candidate solutions from 20 candidates and 0 unique
task IDs. The run used 477.50 seconds, 59 LLM calls, 387,695 client-reserved
tokens, and 112 sandbox starts. The request journal ended with no pending
request or fatal budget error; the raw response sidecar is mode `0600`.

The separate training command produced
`artifacts/p3c-training-offset285-20261101/training.json` with
`skipped_insufficient_verified_tasks`, `verified_unique_task_count: 0`,
`minimum_verified_unique_tasks: 5`, and `weights_updated: false`. P3-C is
therefore not ready to train from this batch; the collection and skip are
diagnostic evidence, not a successful training generation.
